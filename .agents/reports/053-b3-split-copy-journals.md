## Что было сломано

Один файл `<workspace>/.parddefender/pending.tsv` на два хоста при
несовместимых форматах и несовместимых процедурах откат:

| | AE | Premiere |
|---|---|---|
| Колонок | 4 (`ts, key, src, dest`) | 5 (`ts, id, src, dest, part`) |
| Запись | `writeText` — **перезаписывает файл целиком** | `appendText` |
| Откат | удаляет **все** `.pdpart` в папке назначения | удаляет ровно записанный `.pdpart` |
| После отката | удаляет файл целиком | удаляет файл целиком |

Два следствия, оба воспроизводимы при открытых AE и Premiere на одной рабочей
папке:

1. Начало прохода AE **стирало** журнал незавершённого копирования Premiere.
2. Откат AE удалял **все** `.pdpart` в папке назначения — включая тот, в который
   Premiere писал прямо в этот момент. И запускается он не на старте, а на
   **каждую смену проекта** (`onProjectChanged`).

Второе прямо противоречило собственному комментарию модуля: «deleting something
we did not certainly write is the one mistake this whole design exists to avoid».
Причина была в том, что имя `.pdpart` генерировалось случайным и **нигде не
записывалось**, так что опознать свой недописанный файл было нечем — оставалось
подметать папку.

### Механизм: токен задачи

Ключевая часть — не переименование файлов, а то, что AE наконец может опознать
свой недописанный файл.

```
journalTasks:  task.partToken = newPartToken()
               строка журнала: ts \t key \t src \t dest \t partToken
copyOne:       partial = <dest>.<partToken>.pdpart
recoverJournal: в папках из журнала удалить только *.<partToken>.pdpart
```

Один токен на задачу, то есть на все кадры секвенции: задача одна и
откатывается целиком. Для секвенции в журнале лежит **папка**, а не файл,
поэтому откат смотрит и `dirname(dest)`, и сам `dest` — лишний каталог просто не
даёт совпадений, потому что сверка идёт по токену, а не по имени.

Всё, что не опознано, **не удаляется**, а считается: `summary.unattributed`.
Панель сообщает об этом отдельной строкой, нейтральным тоном.

### Старый общий журнал

Файл из версий до 2.3.5 может остаться после сбоя на старой версии. Строки там
различимы по числу колонок: у AE ровно четыре, у Premiere ровно пять. Каждый хост
забирает только свои, **переписывает файл без них** и удаляет его лишь когда
чужих строк не осталось. Откатывать копирование другого хоста — не наше дело: его
недописанные файлы умеет опознавать только он сам.

Строки AE в старом журнале токена не имеют, поэтому опознаются по имени
назначения: `clip.mp4.<что-то>.pdpart` рядом с `clip.mp4`. Кадры секвенции так
опознать нельзя — они остаются на диске. Безвредный мусор лучше удаления по
догадке; `.pdpart` никогда не может попасть в проект.

## Решения и отклонения

1. **Токен, а не «подметать по своему префиксу».** Можно было назвать партиалы
   `*.pd-ae-*.pdpart` и удалять только их. Это развело бы хосты, но не развело
   бы **две копии AE**: вторая панель всё так же сносила бы незавершённое
   копирование первой. Токен привязывает файл к задаче, а не к хосту.
2. **`unattributed` сообщается, а не замалчивается.** Иначе чужой `.pdpart`
   накапливался бы молча, и первая же жалоба «что это за файлы» не имела бы
   объяснения.
3. **Старый журнал не удаляется, пока в нём чужие строки.** Самый простой
   вариант — удалить файл целиком — воспроизводил бы ровно тот баг, который
   правится.
4. **Имена журналов экспортированы (`JOURNAL_NAME`) и используются тестами.**
   Два теста ломались на зашитом `pending.tsv`; ещё один (`журнал прохода убран`,
   из отчёта 051) **продолжал проходить, проверяя несуществующий файл** — то
   есть стал неспособен упасть. Теперь имя во всех трёх берётся из модуля.

**Отклонение:** правки не ограничились переименованием. Без токена требование
«не удалять `.pdpart` друг друга» выполнить нельзя — разделение журналов само по
себе закрывает только первое из двух следствий. Это часть задания, а не
расширение.

**Что сознательно не делалось:** блокировка на журнал. Два прохода в одной
рабочей папке по-прежнему не сериализуются между собой; они просто больше не
портят друг другу данные. Полная сериализация — это `withLock`, у которого свои
проблемы (C-2: busy-wait в UI-потоке и снятие «протухшей» блокировки через 5 с).

## Риски и что не проверено

- Всё на моках; живого ExtendScript и живого UXP не было.
- Связь «`copyOne` использует выданный токен» проверена подписью и модульной
  проверкой `partialNameFor`, но **не** сквозным падением процесса: во всех
  обрабатываемых сбоях код сам убирает `.pdpart`, поэтому наблюдать его можно
  только после настоящего краха. Тесты воспроизводят крах, создавая `.pdpart` с
  тем же именем руками.
- Старый общий журнал обрабатывают оба хоста. Если они сделают это одновременно,
  возможна гонка на перезаписи файла: худший исход — чья-то строка потеряется и
  соответствующий `.pdpart` останется на диске. Файл существует только после
  сбоя на старой версии, то есть это одноразовое и безвредное окно.
- Переименование журналов означает, что `pending-ae.tsv` от версии 2.3.5 старая
  версия расширения не увидит. Откат на предыдущую версию оставит такой файл
  лежать; вреда нет, но и подметён он не будет.
- Сериализации двух проходов в одной рабочей папке по-прежнему нет — только
  отсутствие взаимной порчи.
- Группа C аудита открыта целиком.
